# Study App: Hinweise für Claude Code

Lies zuerst `docs/spec.md`. Dort stehen Ziel, Formeln, Screens und die Reihenfolge für den Ausbau (Abschnitt 10). Dieses Dokument beschreibt, was im Grundgerüst schon steht und wie das Projekt aufgebaut ist.

## Befehle

```bash
npm install          # einmal im Projektordner
npm run dev          # Web-App (Port 5173), erreichbar unter http://localhost:5173/study-app/
npm test             # Logik-Tests (packages/core)
npm run typecheck    # Typprüfung aller Pakete
npm run build        # Produktions-Build der Web-App
```

Die Web-App ist auch im lokalen Netz erreichbar (`vite --host`), so lässt sich der Timer-Abgleich mit dem Handy testen.

## Konventionen

- Oberfläche auf Deutsch, Bezeichner im Code auf Englisch. Die deutschen Feldnamen in `docs/spec.md` entsprechen den englischen Typen in `packages/core/src/types.ts` (zum Beispiel Status `weiter`, `ab_q3_abwaehlen`, `abgewaehlt` sind `active`, `drop_q3`, `dropped`; Fachtyp `aufgaben`, `wissen`, `schreiben` sind `problems`, `knowledge`, `writing`).
- Geschäftslogik nur in `packages/core`, als reine Funktionen mit Tests. Die UI rechnet nichts selbst.
- Manuelle Werte überschreiben automatische. Zu jedem überschriebenen Wert zeigt die UI den Vorschlag der App.
- Farben nur über die CSS-Variablen in `apps/web/src/styles/tokens.css`. Jede Änderung in hell und dunkel prüfen.
- Geheimnisse (später der API-Schlüssel für die KI-Bewertung) nur in Supabase Edge Functions, nie im Frontend. Im Frontend steht nur der öffentliche anon-Schlüssel, geschützt wird über Row Level Security.
- Der Zustand liegt in Supabase. Änderungen laufen über den Reducer in `state/store.tsx`, `state/remote.ts` schreibt sie in die Datenbank. Neue Felder brauchen eine neue Migration unter `supabase/migrations/`.
- Hinweise und Warnungen blockieren nichts, sie empfehlen nur.

## Stand

Fertig im Grundgerüst:
- Logik-Modul mit 21 Tests: Priorität mit Abwahl-Regeln (LK und Prüfungsfach nicht abwählbar), Gesamtzeit, Vorlauf mit Puffer für Schreiben, Lerntage, Limit-Warnung mit spätestem Start, Wiederholungs-Abstand, Zeitleiste, geplante Minuten pro Tag
- Onboarding in fünf Schritten
- Heute: Tagesziel aus dem Plan, gelernte Zeit, nächste Klausur, geplante Blöcke, Aufgaben
- Fokus: Pomodoro mit einstellbaren Längen, Fachauswahl, Leertaste, Abgleich zwischen Geräten über den Server
- Plan: Wochenübersicht geplant und gelernt, Klausurkarten mit Fortschritt und Zeitleiste
- Klausur-Editor: alle Regler mit Vorschlag und Überschreiben, Rahmen (lernfreie Tage, Tageslimit), Warnungen
- Fächer: Status, Fachtyp, Leistungskurs, Prüfungsfach, Note, Schwierigkeit, Priorität mit Aufschlüsselung
- Einstellungen: Hell, Dunkel, Automatisch, Profil, Planung, Daten löschen
- Responsiv: Seitenleiste am Mac, Leiste unten am Handy

Dazu gekommen:
- Supabase als Backend: Anmeldung mit E-Mail und Passwort, Daten pro Konto in Postgres, Timer-Abgleich über Realtime
- Lanis-Import: Klausuren aus dem Schulportal-Kalender (Plan, "Aus Lanis importieren"), Abruf in der Edge Function `lanis-calendar`, das Passwort wird nicht gespeichert
- Konzentrationsscore auf Heute (Check-in von Hand) und Kopplung an die Fitness-App Overload: Overload sendet täglich Anzahl, Dauer, Art und Schlaf an die Edge Function `fitness-ingest` (Verify JWT aus, Prüfung über Verbindungscode, nur der Hash liegt in `fitness_links`). Daten aus Overload gehen der Eingabe von Hand vor. Sender-Seite: Overload-Projekt, Abschnitt "Study App verbinden" **Belastung und 7:28 (seit 9.10.2026, Migration 20261023):** Overload sendet zusätzlich pro Tag `load` (Punkte = Dauer mal Anstrengung, Foster-sRPE), `rpe` (Anstrengung 1 bis 10, nach Minuten gewichtet), `rpeSet` (vom Nutzer in Overload eingestellt oder von Overload geschätzt), `acute` und `chronic` (7-Tage- und 28-Tage-Mittel, EWMA, in Punkten pro Tag) und `ready` (genug Daten, Overload braucht etwa 14 Tage); alles freiwillig, ältere Overload-Versionen senden es nicht, die Function begrenzt und rundet die Werte. Gespeichert in `fitness_daily` (`load`, `rpe`, `rpe_set`, `acute_load`, `chronic_load`, `load_ready`), von Hand im Check-in `daily_checkins.training_rpe`. Wirkung auf den Konzentrationsscore (`concentration.ts`, `CONFIG.concentration.load`): (1) **Training heute** entscheidet bei bekannter Belastung statt der groben Minutenregel: bis `moderateLoadMax` (450 Punkte) und Anstrengung unter `noBonusRpe` (9) leichter Bonus, ab `heavyLoadMin` (600) Dämpfung, dazwischen neutral; von Hand schätzt die App ohne Angabe eine mittlere Anstrengung (`defaultRpe` 5, das entspricht der alten Regel bei einer Einheit). (2) **7:28** (`loadRatio`, `loadStatus` wie in Overload: unter 0,8 erholt, bis 1,3 optimal, bis 1,5 hoch, darüber sehr hoch) dämpft nur bei hoch (0,95) und sehr hoch (0,9), `latestLoadRatio` nimmt den letzten Wert, höchstens `maxAgeDays` (2) alt und nur mit `ready`. Die Anstrengung ändert man in Overload nach dem Training oder in der Konzentrationskarte (nur beim Check-in von Hand). Eine Orientierung, in der Forschung umstritten, keine medizinische Aussage
- Gemeinsamer Plan: `planAll` verteilt alle Klausuren auf die Tage (frühere Frist zuerst, Tageslimit, lernfreie Wochentage, am letzten Tag leichter Spielraum). Ausfälle pro Tag (fällt aus, bis 30 min, 1 h, 2 h) in der Agenda auf der Plan-Seite, der Plan rechnet neu, verpasste Zeit rutscht auf spätere Tage. Realitätscheck pro Klausur, Themenliste im Klausur-Editor
- Lanis-Import erweitert: Stundenplan und Vertretungen (Edge Function `lanis-calendar` liefert Klausuren, `timetableHtml` und Vertretungen, ein Login für alles). Gespeichert als JSON in `lanis_snapshots`. Heute zeigt "Schule heute" mit Freistunden und Vertretungen, der Plan das Wochenraster. Der Vertretungsplan ist nur zum Abrufzeitpunkt aktuell, das Passwort wird nicht gespeichert, also gibt es keinen Abruf im Hintergrund. Das Vertretungsformat stammt aus der Bibliothek der Lanis-Entwickler und ist noch nicht an echten Einträgen geprüft
- **Fehlstunden und DSBmobile (seit 22.10.2026, Migration 20261030):** `lanis-calendar` liefert zusätzlich `absencesHtml` (Teil `absences`: nur die Tabelle `id="anwesend"` von `meinunterricht.php`, Format nach liblanis, Spalten wie „fehlend“, „entschuldigt“ je Kurs, leere Zelle = 0). `parseAbsences` liest sie, gespeichert als `lanis_snapshots` Art `absences` (`state.absences`, `absencesAt`), Abruf alle 12 Stunden, `components/AbsencesCard.tsx` auf Heute nur wenn irgendwo eine Fehlzeit steht. Die Bedeutung der Spalten kommt von der Schule, die App rät nur nach der Beschriftung (`absenceKind`). **DSBmobile:** viele Schulen (auch diese) haben den Vertretungsplan nicht in Lanis. Edge Function `dsb-plan` (Verify JWT an, gleiche Prüfung und Grenze wie `lanis-calendar`, Schlüssel `dsb:`) ruft die inoffizielle Mobile API (`app.dsbcontrol.de/JsonHandler.ashx/GetData`, Anfrage und Antwort gzip + base64) und lädt die HTML-Seiten der Pläne, aber nur https auf dsbcontrol.de oder heinekingmedia.de. Die App liest den Untis-Aufbau selbst (`parseUntisPlan`) und `forStudent` behält nur Einträge der eigenen Stufe (aus den Kurscodes) mit Überschneidung zu einer eigenen Stunde und passendem Fach oder Lehrkraft. Eigene Zugangsdaten, verschlüsselt nur auf dem Gerät (`study-app-dsb-creds`, `components/DsbCard.tsx` in den Einstellungen); ist DSBmobile an, fragt `lanisAuto` Lanis nicht mehr nach Vertretungen. Der Plan braucht den Stundenplan aus Lanis. Erkennt die App den Aufbau nicht (`dsbRecognized`), bleibt der alte Stand und eine Meldung erscheint. **Noch nicht an echten Daten geprüft** (weder Lanis-Fehlzeiten noch DSB-Plan), die Tests nutzen erfundene Beispiele. Deploy: `npx supabase functions deploy dsb-plan` und `lanis-calendar` neu
- Release Notes und Auto-Update: Die Version steht nur im obersten Eintrag von `apps/web/src/releaseNotes.ts` (vite.config.ts liest sie als `__APP_VERSION__` und schreibt `version.json`). **Bei jedem Release einen neuen Eintrag oben ergänzen** (Format JJJJ.MM.TT.N). Die App prüft beim Start, beim Zurückkehren und alle 15 Minuten auf `version.json`, lädt neu, wenn gerade nichts bearbeitet wird (nicht auf /klausur, /import, /start, nicht bei fokussiertem Eingabefeld, Schleifenschutz 10 Minuten) und zeigt die Neuigkeiten einmal

Neue Klausuren mit passendem Fach werden automatisch angelegt, bei bekannten ändert sich nur das Datum
- Mittagspause: Eine Freistunde zwischen `CONFIG.school.lunchAfterPeriod` und `lunchBeforePeriod` (6 und 8, also die 7.) zählt nicht als Lernzeit (`splitFreePeriods`)
- Geräte koppeln (Mac, iPad, Handy): `state/store.tsx` hört über `subscribeChanges` (Supabase Realtime, Tabellen siehe `SYNC_TABLES` in `state/remote.ts`) auf Änderungen und lädt dann alles neu (`refetch`). Eigene, noch nicht gespeicherte Änderungen werden nie überschrieben (`pending` und `localVersion`), beim Zurückkehren in die App und bei wieder verfügbarem Netz wird nachgeholt, weil iOS Verbindungen im Hintergrund trennt. Neue Tabellen mit Nutzerdaten gehören in `SYNC_TABLES` und in die Veröffentlichung `supabase_realtime` (Migration). Einstellungen → Geräte zeigt den Stand
- Layout: unter 768 px Leiste unten (Handy), 768 bis 1099 px schmale Seitenleiste mit Symbolen (iPad hoch und quer), ab 1100 px breite Seitenleiste (Mac). Bei `pointer: coarse` sind Tippflächen mindestens 44 px
- Arbeitsblätter (Seite Notizen): Fotos und PDFs werden im Browser vorbereitet (`lib/resizeImage.ts`, `lib/worksheetFiles.ts` mit pdfjs-dist nachgeladen: Text pro Seite, nur Seiten mit weniger als `CONFIG.ai.minCharsPerPage` Zeichen werden als Bild gerendert), erst danach in den privaten Bucket `worksheets` hochgeladen (`{user_id}/{uuid}.jpg`) und über die Edge Function `summarize-worksheet` (Verify JWT an, Secret `ANTHROPIC_API_KEY`, Modelle je Aufgabe in `CONFIG.ai.models`: `text` und `image` Haiku 5.5 (beide Effort medium), `escalation` Sonnet 5.5 (medium) wenn die Lesbarkeit "unsicher" war und für "Genauer lesen" (dort mit high), `exam` Sonnet 5.5 für die spätere Klausurenkorrektur. Effort über `output_config.effort`, kein `thinking`-Parameter (das Denken zählt zu `max_tokens`) und kein `temperature`, `top_p`, `top_k`, ein Test prüft das) zusammengefasst. Höchstens `CONFIG.ai.maxImagesPerRequest` Bilder pro Anfrage, mehr gehen in Päckchen. Verbrauch pro Monat und Modell in `ai_usage` (eine Zeile je Nutzer, Monat und Modell, nur die Function schreibt, `ai_usage_add` mit `p_model`, Migration 20261018), so sieht man die Kosten pro Modell. **Kostengrenze:** `CONFIG.ai.monthlyBudgetUsd` (5 $, etwa 4,2 bis 4,8 €; die Sicherung rechnet den teuersten Fall pro Anfrage und stoppt darum schon etwas darunter), vor jeder Anfrage wird der schlimmste Fall (`worstCaseUsd`: Eingabe nach oben geschätzt plus volle `maxTokens`) zu den bisherigen Kosten gerechnet und bei Überschreitung nichts an Claude geschickt. Preise stehen je Modell in `CONFIG.ai.prices` und müssen bei Preisänderungen angepasst werden (ein unbekanntes Modell rechnet mit dem teuersten bekannten Preis, Haiku 5.5 gilt bis 100.000 Token Eingabe, darüber ist es teurer). `monthlyRequestCap` (500) ist nur die zweite Sicherung. Notizen in `lesson_notes` (live synchron), Anzeige als kompakte Zeilen nach Woche und Tag (`groupNotesByWeek`), eine Notiz offen, Wochen älter als die letzte zugeklappt, Fachfilter oben. **PDF-Dokument:** `lib/mergePdf.ts` (pdf-lib, nachgeladen) fügt die gewählten Dateien in Listenreihenfolge zu einem PDF zusammen, nur im Browser (PDF-Seiten unverändert, Fotos auf A4, `CONFIG.pdf`). `pages/NoteUpload.tsx` führt in zwei Schritten: Dateien, Fach, Datum, Lehrkraft, Q-Phase wählen und zusammenfügen, dann bestätigen und hochladen (privater Speicher `documents`, Pfad `{user_id}/{uuid}.pdf`, Spalten `pdf_path`, `teacher`, `quarter` an `lesson_notes`). Der Dateiname wird nie gespeichert, sondern aus Datum, Fach, Lehrkraft und Q-Phase berechnet. Die KI-Zusammenfassung ist ein Haken (Standard an); scheitert sie, bleibt die Notiz mit dem PDF. **Tokens sparen:** `preparePages` sortiert vor dem Hochladen aus, was nichts bringt: Dateien, deren SHA-256 schon an einer Notiz steht (`lesson_notes.file_hashes`), leere Seiten (`isBlankPage`, Schwellen `CONFIG.ai.blank*`) und gleiche Seiten. Der Prompt (`summaryPrompt`, Grenzen in `CONFIG.ai.summaryLimits`) hält die Ausgabe kurz, weil Ausgabe fünfmal so viel kostet wie Eingabe. Ohne `crypto.subtle` (zum Beispiel http im Netz) wird nicht aussortiert, aber auch nichts kaputt
- **Kostensparen (seit 11.10.2026):** `CONFIG.ai.autoEscalate` ist aus: Ein „unsicher“ gelesenes Arbeitsblatt wird nicht mehr automatisch mit Sonnet wiederholt (20-mal so teuer wie Haiku), die Notiz bleibt „unsicher“ und „Genauer lesen“ macht es auf Wunsch. `CONFIG.ai.deleteSureImages` ist an: Die Bilder einer Notiz werden nach „sicher“ gelesener Zusammenfassung gelöscht (`dropImagesIfSure` in `lib/worksheetApi.ts`, beim Hochladen und nach „Genauer lesen“), weil nur „Genauer lesen“ (nur bei „unsicher“) sie braucht; das PDF bleibt. Ältere Bilder löscht Einstellungen → Speicher (`components/StorageCleanup.tsx`). Prompt-Caching und die Batch-API bringen hier nichts (Einzelanfragen mit wechselndem Inhalt, Prompts unter der Mindestlänge, Antwort wird sofort gebraucht)

Die Parser bleiben als Sicherung. `generate-exam` bewusst ohne Schema (Diagramme zu verschachtelt). **Kostengrenze bei Bildern:** Die Functions lesen die Maße aus dem JPEG-Kopf (`jpegSize`) und rechnen je Bild `imageTokenBound`: ⌈B/28⌉ x ⌈H/28⌉ plus `CONFIG.ai.imageTokenMargin`, höchstens `maxImageTokens` (4800, Höchstwert der Modelle laut Doku 4784); ohne lesbare Maße der Höchstwert.
